EXECUTIVE VERDICT
=================

The revised plan is materially stronger, but it is still not executable as written.
Proceed with targeted amendments; do not re-plan the product and do not start production code
before the five BLOCKER findings are closed.
The largest risk is the proposed LLM research loop: the two candidate models have different
structured-output, reasoning, and tool-use capabilities, while the plan assumes one common API
contract and budgets up to eight model/tool iterations inside a 20-second response.
The evaluation oracle still cannot test the project’s central correctness claim because the
specified CSV stores verification booleans rather than the factual values an answer must match.
The four-day schedule assumes parallel work that one laptop cannot always execute and names no
owners or gate reviewers.
The differentiation remains credible, but compliance evidence, competitor evidence, and live-demo
fallback semantics need to be tightened before implementation.

DETAILED SECTION 2 — IDEA QUALITY AND GAP ANALYSIS
==================================================

The differentiation is real if implemented at claim/source level: a structured preparation
checklist, prerequisite-document resolution, explicit freshness/change status, and a review queue
solve a more auditable problem than generic chatbot answers (SCOPE §§1, 4-6). It becomes cosmetic
if “fresh” means only an unchanged timestamp, contacts are decorative, or document mappings are
mostly unverified (A08, A24).

The weakest business-case element is still competitor evidence. The existing OMSAR Assistant is
acknowledged, but the comparison is delayed until Jul 28, after architecture and pitch decisions
(TECH_PLAN §9; A25). The documents therefore cannot yet substantiate which queries the incumbent
fails, whether it cites sources, or whether its output is already structured enough to erode the
claimed gap.

The pitch should not claim “a better chatbot.” Use: “an auditable preparation and content-quality
layer for Dawlati that turns procedure sources into claim-linked checklists and routes incomplete
or changed content to OMSAR reviewers.” Citizens are users; OMSAR content operations is the system
owner (SCOPE §1). Lead with first-visit readiness, traceability, and content-review triage.

Do not change the build merely to manufacture novelty. Run the five-query benchmark now and adapt
the wording to observed differences (A25). Restore a small, clearly assumption-based impact model
so business grounding is quantitative without pretending the four-day prototype measured causal
impact (A19).


DETAILED SECTION 3 — FEASIBILITY
================================

The three most likely schedule failures are:

1. Model/tool-loop incompatibility and budget overrun: 80-90% if implemented literally. Blast
   radius: G0, graph, eval, and live demo. The candidates need different adapters, and eight

3. Days 3-4 integration/evidence overload: about 80% without named owners. Blast radius: 90% of
   the grade because report and live demo dominate. The schedule assumes unsupported parallelism
   and leaves competitor/evidence work late (A04, A20-A21, A25).

Playwright over roughly 195 Arabic JS-rendered pages is plausible only after the spike demonstrates
heading/field recall. Hybrid BM25+BGE-M3 with RRF is defensible, but Arabic morphology and
cross-language aliases require holdout testing; G4 is currently too weak (A12). Current public
Groq limits show 8K TPM for both candidates, not the older 6K assumption, but a ~4K composer plus
planning/replanning still exhausts a minute’s budget and threatens the live latency target (A02).
The 24-case eval, three iterations, report, UI, video, and rehearsals do not fit Days 3-4 unless
evidence is captured continuously and work is assigned.

If half a day is lost, cut in this order: follow-up memory; full corpus beyond verified core;
contact enrichment beyond the two-call demo fixture; automated diff recrawl; per-document live
freshness while retaining main-service check; UI polish. Never cut 20+ cases, actual prompt
evidence, two failure analyses, the visible tool loop, the report, or the genuine live demo path

DETAILED SECTION 5 — TECH STACK
===============================

LangGraph 1.2 is defensible but not necessary for every deterministic operation. Keep it for visible
state/trace control; implement HTTP timeouts in the client and avoid relying on async-only node
timeouts (TECH_PLAN §§1,4). Groq is speed/cost-defensible, but the proposed models are not
drop-in equivalents: strict output, reasoning, and tool behavior require model adapters (A01).
Qwen is Preview and neither candidate is a provider fallback (A30).

BGE-M3 is a defensible cross-lingual dense model; it is not “optimal” until measured on the actual
laptop and project queries. BM25+dense with RRF is preferable to incomparable raw-score fusion,
but calibration and holdout separation are still missing (A12). Chroma is acceptable for this
small corpus; a NumPy/JSON index could be simpler, but switching now has little payoff.

Playwright is justified by the known client rendering. Its risk is extraction, not browser choice;
retain it only after the stored field-level spike passes (A13). Streamlit is optimal for speed, but
the HTML/RTL wrapper must escape dynamic content (A29). Pydantic is appropriate and should become
the single source of truth, not an implementation detail deferred beyond G0 (A05, A07).

Local JSONL is a sound replacement for LangSmith under privacy/time constraints, but it needs
locking and one event schema where concurrent tools write (A09). The character-based language
heuristic is acceptable for routing if mixed/short-query behavior is explicit; an additional
language model would add risk without clear value.

Re-verify live before building: exact Groq model availability, account quotas, request parameters,
structured output/tool compatibility, Qwen Preview behavior, and the chosen LangGraph/Groq SDK
APIs. Current official docs support A01, A02, and A30 but may change.


DETAILED SECTION 6 — ARCHITECTURE AND METHODOLOGY
=================================================

The nine-node graph is mildly over-engineered for four days, especially if deterministic
validation, freshness, and response formatting are separate graph nodes only to inflate the
diagram. Preserve the visible research decision boundary and trace, but collapse mechanics where
that reduces integration surfaces (TECH_PLAN §4).

The research loop is simultaneously over- and under-engineered: eight unrestricted calls are too
expensive, yet the gate does not prove that observations alter behavior. Use one plan, batched
tools, and at most one conditional re-plan with a trace oracle (A02, A26).

Depth-1 document resolution is a good scope boundary, but it is unsafe without normalization,
collision, and abstention rules (A11). Per-source freshness is conceptually strong, but
modified_gmt detects changes rather than truth/currentness, and lookup dates need an expiry policy
(A08). Queue writes need a concurrency-safe contract (A09).

The curated-core confidence formula is methodologically unsound if presented as probability:
curation status is not calibrated correctness. Present an evidence-quality score or calibrate
(A23).

The revised eval’s provenance rule—every source_url must occur in retrieved context or the lookup
table—is useful for source laundering detection, not hallucination detection. A cited source may
fail to support the claim, and a correct claim can use an allowed URL. Claim-level expected values
plus excerpts/manual entailment audits are required (A03). Likewise, the retrieval calibration set
cannot double as the final quality test (A12).

Under-engineered live-demo areas are contact endpoint coverage, provider outage behavior, typed
partial-result semantics, duration arithmetic, and safe Arabic/HTML rendering (A06, A10, A14-A15,
A29). These are precisely the failures a grader can expose during Q&A.

DETAILED SECTION 8 — VERIFICATION-GATE QUALITY
==============================================

G0 is the most urgent gate but is circular until the bootstrap schema/adapter exception is written
(A05). It must test each candidate through its real production-shaped path, not impose identical
unsupported settings (A01). Contact viability should be a G0/G1 subgate because it determines
brief compliance (A06).

G1 needs contact post types and denominators if get_contacts remains in scope (A27). G2’s manual
oracle must be stored and cover all answer fields, not only document extraction (A13). G3 should
verify every lookup row used in the core/demo, not five of twenty (A24).

G4 is too easy and risks test leakage: split calibration from holdout and replace 70% top-1 with
90% top-1-or-correct-clarification on core holdout (A12). G5’s dependency is wrong unless fixtures
are created in G0 (A22).

G6’s <=20-second and up-to-eight-call requirements conflict (A02); its “reaction” criterion needs
an automated observation-dependent trace fixture (A26). It also depends on unverified contacts
(A06). G7 must inject a dead REST dependency rather than turn off all networking (A14) and should
test queue concurrency/deduplication (A09).

G8 cannot evaluate factual correctness until real gold claims exist (A03). It must require mean
latency (A28), two failure narratives (A18), and a separate holdout. G9 should test escaped
adversarial HTML/RTL content (A29). G10 must validate exact prompts/few-shots and exact AI-log
evidence, plus all required appendices (A16-A17, A20). G11 should distinguish Dawlati-source
failure, Groq-provider failure, and emergency cached playback; cached mode is not the primary live
demo (A14-A15, A30).

The dependency chain should allow truly synthetic G5 fixtures after G0, but real-index G6 must wait
for G4. Report/evidence work can run continuously; model/download/crawl/index tasks cannot be
assumed parallel on one laptop (A04).

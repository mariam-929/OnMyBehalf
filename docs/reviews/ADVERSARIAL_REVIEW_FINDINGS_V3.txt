N1 | MAJOR | regression (contradicts A10/FR5 + graded hallucination count)
References: prompts/composer_v1.md lines 42-46; SCOPE.md FR5; SCHEMA_AND_CONTRACTS.md 3.
Finding: The composer few-shot shows INPUT evidence "service time=[5,10] business_days" with both
documents corpus-resolved, then emits OUTPUT time_estimate {computable:true, total_min_days:7,
total_max_days:15}. The addends that turn [5,10] into [7,15] (the documents' own durations) are
NEVER shown in the input evidence. A few-shot exemplar is imitated by the model; this one teaches
it to (a) invent durations for documents whose duration is unknown and (b) sum them into a single
total. That directly feeds the graded hallucination count (CLAUDE.md: "never invent queue/wait
times ... graders count hallucinations") and violates FR5 (aggregate only same-unit *stated*
durations). It also disagrees with the SCHEMA sec.3 gold for the same passport case, whose
stated_processing is {5,10}.
Fix: Rewrite the exemplar so every number is derivable from shown evidence: either show each
document's stated duration in the input, or set total = service-only with is_lower_bound=true, or
if any component unit is unknown set computable=false and present component-wise.
Owner: __  Reviewer: __
Closure artifact: corrected composer_v1 (or v2) few-shot; G6/G8 hallucination audit finds 0 invented
durations on the core case.
Blocks code now? No — resolve before the first composer run / at prompt iteration; do now (cheap).

N3 | MAJOR | residual (bounded-loop budget vs FR6b; implementation ambiguity)
References: SCOPE.md FR6b + 5; prompts/research_agent_v1.md lines 17-23; VERIFICATION.md G6, G7.
Finding: Two problems with per-document freshness inside the bounded loop:
 (a) Contention for the single re-plan. A document's post_id is known only AFTER round-1
     resolve_document returns, so per-doc check_freshness must go in round 2 (the one allowed
     re-plan). But the protocol reserves that revision for "retry resolve_document with a normalized
     alias." The two uses collide: spend round 2 on freshness OR on alias-retry, not both. The
     few-shot plan only freshness-checks the service, never the documents.
 (b) Tool-budget overflow. 1 service-freshness + 1 live_lookup + N resolves + N per-doc freshness
     = 2 + 2N tool calls. For N>=3 that is >=8; for N>=4 it exceeds the <=8 tool cap (A02).
 Whether per-doc freshness is model-planned or system-automatic is unspecified — a coding agent must
 guess, and G7 auto-checks "per-document freshness populated."
Fix: State in SCOPE 5 / research_agent_v1 that per-document check_freshness runs DETERMINISTICALLY by
the system on each corpus-resolved post_id after resolution (so it does NOT consume the model
re-plan, freeing the re-plan for alias-retry), and define behavior when 2+2N exceeds 8 (cap +
degrade to service-only freshness, consistent with SCOPE 15 cut-order item 4).
Owner: __  Reviewer: __
Closure artifact: G6 shows the re-plan used for alias-retry; G7 shows per-doc freshness populated
without exceeding the tool budget.
Blocks code now? No — resolve at G6/G7; clarify now (one sentence).
Residual risk: if left, either the re-plan is unavailable for alias-retry, or per-doc freshness
silently drops, or the <=8 budget is violated on realistic multi-doc services.
